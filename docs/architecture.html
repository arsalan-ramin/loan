01 / Executive overview

The application stores one shared, latest complete Query 1/2/4 dataset. Users can reuse it across sessions without repeatedly uploading workbooks. Source rows and their explicit relationship IDs are indexed in SQLite. A selected loan is reconstructed from the relevant rows, not by sending entire workbooks to a language model.

React UI — upload three workbooks, reuse stored data, select a loan, or start a batch
HTTP /api ↓
FastAPI intake + background indexing — validate roles, preserve source bytes, stream rows, map explicit IDs
Transactions + relationship indexes ↓
Local SQLite dataset — workbook manifest, source records, key index, loan/account directories
Loan-scoped relationship closure ↓
EntityGraph + deterministic engine — canonical fields, provenance, strict diagnostics, separate TEST decision
Allowlisted normalized facts, fixed outcomes and citation IDs ↓
Claude explanation + output validation — narrative only; cannot replace the engine's decision
Persisted JSON / UI / HTML / JSON / CSV / batch Excel ↓
Review artifacts — session reports, per-loan audits and latest batch results
Three different outputs must not be confused. The TEST demo produces Approve / Decline / Refer; batch display maps Approve to Approved. The enclosing underwriting contract remains non-operational, with authorization=NOT_ISSUED. Claude produces commentary, not a lending authorization.

This document describes the implementation, including business FICO and interactive loan-number chat processing. It is not an approved lending policy. Examples use fabricated IDs and values, not client data.

03 / How data is ingested

Step A — receive and save source bytes

  1. The browser submits multipart/form-data, with each workbook in the files field, to POST /api/sessions/{session_id}/documents.
  2. The API requires an editable session and nonempty supported files. MTB sessions accept at most three XLSX files, allow incremental uploads, and cannot mix XLSX with other formats.
  3. Each file is written in 1 MiB chunks under uploads/{session_id}/{document_id}. The original basename is retained in the Document; storage names are opaque IDs.
  4. Upload invalidates the previous selection/report/preflight and document retrieval entries for that session. It does not automatically execute a loan decision.
  5. When the session contains exactly three XLSX documents, the API submits a shared-dataset indexing job to a single-worker executor.

Step B — identify the complete Query 1/2/4 set

The dataset job stages source files using hard links where possible and copies otherwise. A headers-only read identifies query roles from recognized filenames or header signatures. Exactly one workbook for each role 1, 2, 4 is required. Recognition selects the mapping family; it does not prove that all decision inputs are present.

WorkbookMain contributionImportant links/fields
Query 1Loans, accounts, Entity Involvement rows, financial observations and nested credit reports; first-choice FICO and borrower-row SBSS.LLC_BI__Loan__c, LLC_BI__Account__c, LLC_BI__Borrower_Type__c, nested nFUSE__Credit_Report__r.nFUSE__Credit_Score__c.
Query 2SBSS and LCR entity/response/analysis/indicator relationships.Explicit loan ID and response/entity/account relationships; supplied SCOC__SBSS7Score__c.

Step C — replace, stream and index

  1. Compute SHA-256 for each staged workbook. An identical filename/hash set with the current mapping fingerprint is a no-op: existing data and batch results are retained.
  2. For a different valid complete set, clear shared dataset tables, stored dataset XLSX files and latest batch data first. Mark the store indexing.
  3. Place new uniquely named workbook files. Parse with openpyxl using read_only=True, data_only=False, keep_links=False.
  4. Preserve sheet name, Excel row number, values, cell coordinates, row text and formula count. Reference sheets named README, instructions or guidelines are not treated as loan data rows.
  5. Map each data row's explicit IDs with record_mapper(). Save the row once in dataset_records and flatten its mapped IDs into dataset_keys. Flush inserts every 2,000 records, inside one indexing transaction.
  6. Build loan/account directories from persisted records in 5,000-row chunks. Store counts and fingerprint, run ANALYZE, then commit with status=ready.
Replacement is clear-then-load, not an atomic old/new dataset swap. Incomplete or unrecognized sets do not clear existing data. Once a valid replacement starts clearing, however, the previous shared dataset is gone. If indexing fails, rollback and cleanup leave a failed store requiring another upload. Older session uploads/reports and Chroma history are not globally deleted.

Formula handling: formulas are preserved as descriptive text, but their mapped values are null. Neither cached formula results nor Excel expressions are evaluated. Duplicate populated column headers are rejected as ambiguous. The backend does not impose a general upload byte cap; disk, memory and parsing time still impose practical limits.

Sources: upload_documents(), identify_roles(), replace(), _clear(), _index(), extract_excel().

The relationship index is covering for its four stored columns. Scoped queries seek candidate record IDs and then fetch source rows by integer primary key. Directory search uses case-insensitive prefix ranges, not arbitrary substring search. Pagination and count queries still cost work; indexes do not guarantee a fixed response-time SLA.

SQLite configuration: shared dataset uses WAL journaling, a 60-second connection timeout, in-memory temporary tables and a 64 MiB suggested page cache per connection. Explicit transactions and BEGIN IMMEDIATE serialize writes. Connections are closed to release Windows file locks. No SQL foreign-key constraints are declared for dataset_keys; linkage correctness is application-managed.

Session database and retrieval memory

  • sessions(id PK, updated_at, payload) stores the full Pydantic Session.model_dump_json(). Reads use Session.model_validate_json().
  • account_candidates, account_candidate_loans and loan_directory contain session-specific search directories with composite primary keys and session/name/loan lookup indexes.
  • Chroma collection folio_memory stores document/conversation chunks with session, kind and source metadata. Embeddings are local 384-dimensional feature-hashed token vectors, not neural embeddings or an external embedding API.
  • Recall filters by session and optional kind, requests four neighbors and keeps cosine distances below 0.95. This memory helps chat, not deterministic joins or loan decisions.

05 / How a loan is retrieved quickly

  1. Attach stored workbooks: POST /api/sessions/{id}/stored-dataset requires an empty editable session and a ready dataset. It creates new session Document objects and hard-links/copies the stored workbook bytes into the session upload directory.
  2. Validate exact input identity: the loader hashes session workbooks. Indexed retrieval is eligible only when names/hashes match the stored files and the mapping fingerprint is current.
  3. Seed closure: initialize related IDs with the exact selected loan ID. Temporary dataset_frontier rows hold table/key/value lookups.
  4. Seek connected rows: join frontier entries to dataset_keys_lookup, then to dataset_records by primary key. Explicit different-loan rows are excluded.
  5. Expand relationships: accepted rows reveal account, report, response, entity and analysis IDs. Continue until no new IDs remain; evaluate each candidate source record only once.
  6. Rebuild scoped Documents: populate only retained metadata.records, source coordinates, sheet row text and scope counts in original source order.
  7. Fallback for single-loan reviews: if the store is unavailable/stale or the bytes differ, stream workbooks repeatedly until explicit relationships stabilize. Use the same mapper and acceptance logic. Batch instead stops when its indexed dataset no longer matches.
Loan L-DEMO-001
  -- EntityInvolvement.loan_id --> involvement rows
       -- account_id -----------> business + linked accounts
            -- CreditReport.account_id --> Q1/Q4 credit evidence
  -- response/entity relationships --> Query 2 LCR data
       -- analysis_id ----------------> indicators/characteristics
No positional or name joins. Rows are connected using explicit Salesforce/canonical IDs. A generic root Id is not assigned to every entity represented by a flattened SOQL row. Query 4 account IDs must match the accounts linked to this loan, not just a displayed borrower name.

Graph construction: build_entity_graph() turns the scoped records into EntityNode(table, id, fields, evidence, field_refs, poisoned) objects. Conflicting duplicate fields keep their provenance and are marked poisoned instead of silently overwritten. TEST score-selection overrides are applied separately; they do not mutate or clear conflicts in the strict graph.

Sources: attach(), load_scoped(), _load_scoped(), accept(), load_loan_documents(), EntityGraph.

07 / How the decision flow is applied

Two isolated evaluation tracks

evaluate_underwriting() builds the graph and evaluates strict v4/implementation/expanded diagnostics. In TEST it additionally calls evaluate_demo() and places the result under normalized_data.demo_decision. The demo does not rewrite strict report selection, missing inputs, policy conflicts or recommendation paths. PRODUCTION does not execute the TEST demo and requires manual review.

Borrower identity

Use the single account carrying the Borrower role. If that is ambiguous or absent, prefer the unique Business account among Borrower-role accounts, then among all explicitly linked accounts. If no literal Business type qualifies, a nonblank type other than Individual can qualify as a business entity. Unresolved identity prevents approval; a known knockout can still produce a demo Decline.

FICO source selection and averaging

  1. Collect every account linked to the loan, including the business and guarantors, regardless of the Query 1 role label. Count each account once.
  2. Read the first nonblank account-linked Query 1 score in source order. A repeated Query 1 report with conflicting score values alone uses its first nonblank score evidence.
  3. Accept finite numeric scores in the inclusive range 300–900. If Query 1 is absent, blank or invalid, scan that same account's Query 4 reports in source order and use the first valid score. Skip invalid Query 4 rows; repeated report IDs and Id-less rows are supported.
  4. A valid Query 1 score wins even if Query 4 has a different score. Do not choose by report freshness/completion and do not average multiple reports for one account.
  5. Average valid selected account scores using Decimal. Missing or invalid scores with no usable fallback are left out of sum and denominator, not treated as zero. With no usable score, aggregate FICO is unknown.
  6. Conflicting account types, conflicting report identity/typing and untyped generic scores can block the aggregate. Invalid scores alone do not.

Example: business 780 from Query 1 + guarantor 720 from Query 4 + linked account with no valid score gives (780 + 720) / 2 = 750, not 500. A score of 94.57 is outside the accepted range and is not rescaled.

SBSS source priority

First use valid integer SBSS 0–300 on the business borrower's Query 1 Entity Involvement row for this loan. If several valid borrower-row values exist, use the lowest. Otherwise use linked Query 2/loan-level SBSS. For conflicting loan-level values, use a unique borrower-row observation when available, otherwise the lowest of the applicable observations.

Knockouts — evaluate first

  • Bankruptcy: failed verified clearance is a knockout.
  • FICO: average below 650 is a knockout.
  • SBSS: below 160 is a knockout.

Any known failed knockout yields Decline / KNOWN_KNOCKOUT, even when another input is unknown. Unknown is neither failure nor clearance. Age/DOB, EBITDA and public-record-code observations are non-gating diagnostics in this TEST demo.

bounded_demo_context() allows normalized scalar facts, known branch/status/basis names, limited criteria and allowed evidence IDs. It excludes raw rows, arbitrary source text, full per-account FICO audits and strict policy diagnostics. Criteria statuses are reconciled with normalized values so stale saved flags cannot describe SBSS 177 as below 160. Evidence has a global 40-ID budget; at most 20 loans are included. Selected-loan review narrows to that loan before applying the bounds.

Prompt alignment: DEMO_SYSTEM includes business and guarantor FICO in 300–900, respects the applied bankruptcy/vehicle/ownership defaults, and limits Refer explanations to supplied missing_inputs and conflicts. Age, EBITDA and public records are explicitly non-gating. Missing NAICS is relevant only on the SBSS ≥200 / ownership ≥2 branch. A missing unique borrower link remains a real blocker. Saved batch rows must be reprocessed after deployment; current validation still does not fully verify narrative semantics.

Validation and transport behavior

  • Parse with Pydantic models that forbid extra fields. Selected output fixes recommended_route=MANUAL_REVIEW, null recommendation/confidence and human approval true.
  • Verify exactly the selected loan ID, allowed failed-rule IDs, and supplied evidence IDs. Strict unresolved checks must be reconciled exactly once using only their own references; TEST demo has no strict checks to reconcile.
  • Validation does not prove every natural-language statement matches the branch, label or score. The deterministic engine result is kept separately from Claude's prose.
  • The default configured model is claude-sonnet-5-5, overridable by ANTHROPIC_MODEL; provider credentials and endpoint configuration are server-only.
  • Each invocation has an 8,192 output-token ceiling and a 60-second SDK timeout. SDK retries are disabled; the application owns bounded retries for eligible transient failures, rate limits and connection errors (default two retries).
  • Truncated, empty or abnormal-stop responses are rejected. Provider/configuration errors are explicit; no synthetic success explanation is substituted. A normal single-session report can retain deterministic results with llm_error.

09 / How batch review works

  1. Start only with a ready nonempty stored dataset and configured Anthropic key. The UI asks for paid-call confirmation.
  2. A full new run clears previous batch results and writes the singleton batch_run with the current dataset timestamp and model.
  3. A coordinator thread attaches source workbooks to a temporary job directory. It queues discovered loans in case-insensitive loan-ID order.
  4. A thread pool processes independent loans; BATCH_REVIEW_CONCURRENCY defaults to 4 and is clamped to 1–16.
  5. Each worker deep-copies document templates, retrieves that loan's indexed rows, calls evaluate_underwriting(..., "TEST", selected_loan_id=...), reads demo_decision.label and builds its full linked-account display.
  6. Create an in-memory completed session/report for that one loan and use review_selected_loan() for Claude's explanation. This is one logical paid commentary invocation per evaluated loan; transient transport retries can add provider requests.
  7. Persist status, branch, deterministic rationale, Claude rationale, error, model, timestamp and account-list JSON. Save only while the batch and shared dataset timestamps still match.
  8. The UI polls progress and paginated results. Excel export writes Loan ID, Accounts, Status, Rationale / result; Accounts lists type, roles and FICO used or why omitted. Cells that could be interpreted as formulas are escaped.

Decision vs processing

A row can have a deterministic Approved / Decline / Refer status and still have processing=failed because the rationale call failed. The error is separate from the decision; retries target failed processing.

Cancel, resume and retry

Cancel stops new submissions and waits for in-flight work. Resume skips succeeded records; selected/all-failed retry replaces those results in place. A changed dataset invalidates resume/retry against an old run.

Provider configuration/authentication/unavailable-model errors stop the run. Other per-loan provider/validation errors are stored and the run can continue. Restart marks a running batch interrupted. Batch persistence stores summarized results, not the complete per-loan report/context/prompt; single-session reports carry the richer JSON trace.

Source: BatchReviewer.

10 / API and UI lifecycle

Interactive Agent conversation

  1. Agent greets the user locally and asks for a loan number. The greeting and composer disclose that sending the number starts a review with a billable Claude explanation.
  2. POST /api/sessions/{id}/messages recognizes one exact number such as L1, loan # L1, loan number L1 or process loan L1. Ordinary questions and attribute inventories are not processing commands.
  3. An empty session attaches ready stored data automatically. A session with uploaded workbooks uses those files, not a silent replacement. Missing sources, incomplete sets and unknown loans return explicit errors before a review is queued.
  4. Reuse the existing scoped selection and processing validation. Persist the user's message and progress reply, set status=processing and submit the existing worker. The message API returns HTTP 200; no separate process-button click is needed.
  5. The UI polls the session. Completion appends the deterministic result, branch/route, simulation boundary and Claude explanation to the same saved chat. A provider failure is displayed alongside the retained deterministic result; a processing failure appends a clear failure message.
  6. Another loan number starts a fresh scoped review using the same files, preserving prior chat messages. Concurrent starts while processing are rejected. The transcript contains only messages, progress and results, not forms or action cards. File management and manual review tools are collapsed outside the conversation; the composer paperclip remains available for attachments. This application-owned path does not give the language model tool-execution authority.

Isolated aggregate-FICO what-if

After a completed TEST review, a command such as What if the credit score/FICO was 820? is intercepted locally by what_if.py. It overrides only the aggregate FICO in a deep copy of the saved normalized facts and criteria, then calls the shared decide_demo_facts() TEST tree. All other inputs stay fixed. A higher FICO can change the branch but cannot clear an unchanged SBSS knockout. The reply compares the baseline and hypothetical result; only the chat messages are persisted. Source rows, stored scores, the original report and batch results remain unchanged. No provider call or tokens are consumed. Each scenario starts from the saved baseline; ambiguous, account-specific, multi-field and chained scenarios are not silently interpreted. Scores must be 300–900 inclusive. PRODUCTION is not evaluated.

Ordinary TEST follow-ups use demo_explanation_context() rather than the strict report_context(); strict preflight diagnostics, generic rules and the policy catalog are excluded from that context. Dedicated TEST chat instructions prevent old strict diagnostics and hypothetical user assertions from becoming new decision inputs.

Single-session five-stage pipeline

Intake validates documents/checks → Extraction reloads scoped workbook rows → Rules evaluates optional document checks → Decision runs underwriting and one bounded aggregate explanation → Memory indexes extracted content and conversation locally. Session JSON is saved at checkpoints, while preserving concurrently saved chat messages. The completion result is then persisted as an assistant message; this reuses the existing explanation, not a second paid selected-loan call.

11 / Operations, boundaries and known caveats

ConcernCurrent behavior / implication
Mapping changesFingerprint includes schema version, mapping manifest and loader/mapping source bytes. Startup automatically reindexes retained files when stale. This clears latest batch results. A decision-only change is not covered by that mapping fingerprint; re-run reviews to update saved outcomes.
Interrupted workIndexing interrupted by restart becomes failed and needs re-upload. Processing sessions become failed/retryable. Running batches become interrupted/resumable.
Shared dataset ownershipLatest dataset and batch are application-wide, not tenant-scoped. Session scoping is a data organization/retrieval mechanism, not an authentication or authorization boundary.
Deployment topologyExecutors, locks, singleton dataset objects and job state are in process. There is no distributed queue or cross-process job coordinator. Multiple server processes are not automatically coordinated by these Python locks.
DurabilitySQLite and source files survive restart. In-flight threads do not. Backups need session, dataset and usage databases plus the required workbook/upload files; Chroma is separate retrieval state.
Provider dataSelected/batch reviews send normalized decision context, not raw workbook rows. Chat sends bounded conversation, metadata and permitted excerpts. This document does not assert regulatory compliance or a provider retention policy.
Prompt alignment and legacy resultsDEMO_SYSTEM now matches business FICO, applied defaults and non-gating diagnostics. Legacy “personal” aggregation/status labels remain. Existing saved results are not automatically rewritten; restart/deploy and start a new batch to refresh them.
Audit limitationsEvidence IDs and deterministic facts are retained locally; batch saves summarized outcomes/accounts. No immutable full prompt/response archive, complete decision-history store or model-version replay mechanism is implemented by this batch path.
Policy boundariesTEST assumptions are not production policy. Screenshot USD100K/USD100M conflict is intentionally unresolved. Strict diagnostics can remain unknown even when the independent demo has enough data to produce its label.
Performance claimsIndexed closure avoids repeated full workbook parsing. No measured latency target is guaranteed here. Large scopes, prefix counts, initial file hashing, SQLite write contention and paid provider latency still affect total runtime.

Diagnostics: requests carry X-Request-ID; application logging records request/LLM categories, durations and available token counts. Provider bodies, credentials and prompts are not included in the transport's diagnostic logs. Validation logs use application-owned categories rather than reproducing invalid model output.

Persistent token accounting

The sidebar's Token usage screen shows every recorded Claude invocation and workspace/session totals, refreshing every five seconds. usage.sqlite3 is independent of dataset replacement and batch-result deletion. Its llm_usage table stores invocation ID, timestamps, HTTP request ID when available, session/loan/batch scope, operation, model, status/category, attempts, duration and four token counters. Time and session/time indexes support paginated history. HTTP context is explicitly copied into the session worker; batch workers bind their own batch/loan context.

Each invocation is inserted before the paid request and finalized after completion or failure. Total reported tokens sum uncached input, output, cache-creation input and cache-read input; cumulative totals cover the entire selected scope, not the current page. Retries share one invocation row and expose attempt count. Provider-returned usage counts even for truncated/discarded text or later application validation rejection. Transport success does not imply accepted commentary. Failed attempts without reported usage remain unknown, not zero; reported totals can understate actual billable usage. On restart, unfinished invocations become interrupted. No old usage is reconstructed and no monetary billing estimate is claimed.

The ledger stores no prompts, responses, raw source values or credentials. Accounting write failures are explicit: an initial failure prevents the provider call; a final failure warns that charges may already have occurred. Local greetings, deterministic lookups and decisions create no Claude invocation. These are shared-workspace counters, not tenant-isolated accounting.
