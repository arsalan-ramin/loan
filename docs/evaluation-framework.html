Production boundary

Evaluation is evidence, not authorization. Production behavior remains within the approved authority tier; a passing score cannot bypass a human approval or control.

Critical decisions to unblock

  • Evaluation / data tooling decision and owner
  • Data owner approval per source; privacy and retention alignment
  • Model risk thresholds, release gate, and exception authority
  • Control Tower / MRM registration and incident playbook

Gate evidence

Every release records dataset and model versions, scorecard, threshold result, reviewer / approver, open exceptions, and the decision made.

Minimum viable design | shared across offline and production

Measures | define thresholds by risk tier

  • Outcome / task correctness and completeness
  • Evidence coverage, citation validity, and groundedness
  • Policy / safety violations, escalation and override rate
  • Latency, failure rate, tokens, and cost per task

Golden cases + trace record

Store approved or synthetic inputs, expected outcome, evidence IDs, labels, risk slice, and dataset version. Link each run to prompt / model versions, retrieval, output, scores, latency, cost, reviewer, and result.

Release gate | no single score

Require minimum per-risk thresholds, no critical safety regression, documented exceptions, and named approval. Use human review for ambiguous or high-impact outcomes; re-evaluate after material changes.

01 / Evaluation scorecard | proposed measures

Keep deterministic checks as the first line of defense. Use model-based judges and human review where quality cannot be reliably captured by code alone. Set thresholds by use case and risk tier; calibrate them on reviewed examples before making them release gates.

Judge quality is itself evaluated

Calibrate judge rubrics against a human-reviewed sample, monitor inter-rater agreement and false passes, pin judge model / prompt versions, and route ambiguous or high-risk cases to a person. A judge score is supporting evidence, not ground truth.

Report distributions, not just averages

Show pass rate and confidence alongside failure examples and slices by product, risk tier, language, data quality, and workflow path. Record sample size; define minimum coverage before a result can qualify as a release gate.

02 / Golden dataset | governed learning loop

Golden data is a reviewed benchmark, not a bulk copy of production traffic. Treat case selection, labels, access, and set membership as governed changes with traceable ownership.

Case record | minimum fields

  • Stable case ID, use case, risk tier, and dataset / split version
  • Approved input or synthetic equivalent; source and permitted-use metadata
  • Expected result, acceptable range / rubric, required evidence references
  • Edge-case tags, label provenance, reviewer, approval date, and change history

Lifecycle | intake to regression

  • Start with representative, edge, and known-failure cases; exclude unapproved data
  • Have subject-matter reviewers adjudicate ambiguous labels and disagreements
  • Separate development examples from a held-out regression set
  • Promote sanitized, reviewed production failures into the suite through change control

Governance rule: dataset edits are versioned and reviewed; evaluation results pin the exact dataset version. Do not tune against the held-out set, and do not send regulated or confidential records to a vendor until security, privacy, residency, retention, and contractual controls are approved.

03 / Tooling shortlist | LangSmith + Arize

Propose a time-boxed proof of concept for both options against the same sanitized golden set and workflow. Product capabilities below reflect vendor documentation; enterprise fit, deployment, cost, retention, and data handling need direct validation with the vendors and internal control owners.

LangSmith

Managed evaluation + observability platform

Strong candidate for the integrated developer workflow: instrument application runs, inspect traces, run offline dataset experiments, compare versions, and apply online evaluators to sampled production interactions.

  • Test dataset workflows, evaluator authoring, experiment comparisons, trace search, and feedback capture.
  • Check framework fit, self-hosted / hybrid options, data controls, access model, retention, and total cost.
  • Potential preference when teams prioritize an integrated prompt / agent iteration loop.

Arize

Compare Phoenix (open source) and Arize AX (managed)

Phoenix is an open-source, OpenTelemetry / OpenInference-oriented option for traces, evaluations, annotations, datasets, and experiments. Arize AX is the managed enterprise platform option for observing, evaluating, and improving agents.

  • Test instrumentation portability, trace / span coverage, evaluation workflow, and experiment comparison.
  • Decide separately whether self-managed Phoenix or managed AX meets operating and control needs.
  • Potential preference when open standards, deployment flexibility, or Arize's managed workflow is a priority.
