Production boundary

A passing test does not grant new permissions. A read-only agent still cannot write to a system, and an action that requires approval still needs it.

Decisions before launch

  • AI Platform: select the tool and name its owner.
  • Data owners: approve which data can be tested, logged, or exported.
  • Model Risk and Control Tower: confirm release limits, exception authority, and incident response.

Gate evidence

Every release records dataset and model versions, scorecard, threshold result, reviewer / approver, open exceptions, and the decision made.

Worked example | internal policy assistant

The assistant answers staff questions from approved policy documents. The case and numbers below are illustrative, not bank policy or approved thresholds.

Golden case | what should happen

  • Input: A staff user with access to the policy asks, “When do I need a receipt for an expense?”
  • Expected: “A receipt is required for expenses of $25 or more.” Cite Expense Policy, version 3, section 4.
  • Failure: “Over $25” is wrong because it excludes exactly $25.

Offline | why the release is blocked

  • Answer check: Require 95/100. The new build gets 98/100; the current build gets 96/100.
  • Access check: Require zero disclosures in 20 tests. The new build shows a restricted citation in one test.
  • Decision: Block the release. Fix the disclosure and rerun both sets.

Production | what to check after release

After the fixed build is approved and deployed, sample live requests. If 80 sampled answers require citations and four omit them, report 4 of 80 answers missing a required citation (5%). Send those four traces to the app team. This measures citation coverage, not answer accuracy.

02 / Golden dataset | build a reviewed test set

A golden dataset is a set of approved test inputs with reviewed expected results. Start with synthetic cases or approved data, not a copy of production traffic.

Case record | minimum fields

  • Case ID, use case, dataset version, and whether the case is for tuning or release testing.
  • Input, caller role, and any source documents the caller can access.
  • Expected result, how to score it, and any required citation.
  • Case type, reviewer, and approval date.

How to add and update cases

  • Cover common questions, boundary values such as exactly $25, and requests for restricted material.
  • Have a subject-matter reviewer confirm each expected result.
  • Keep release tests separate from examples used to tune the assistant.
  • Remove sensitive details from live failures and get approval before adding them as tests.

Data rule: approve dataset edits and record the exact version used in each run. Do not export confidential or regulated records without approval for the specific data, destination, and retention period.

03 / Centralized platform | what teams share and what stays private

Teams use one registry, one way to start a test, and one place to see release results. Restricted inputs, raw traces, and case-level results stay in approved workspaces. The shared dashboard shows permitted summaries and links that still require workspace access.

What each run records

Save the run ID, use case, environment, app build, and versions of the model, prompt, checks, and release rules. Offline runs also record the test set and comparison build. Live runs record the sampling policy. Save tested and passed counts, links to cases or traces, and any release decision or exception.

Who owns what

AI Platform runs the service. App teams write tests, send traces, and fix failures. Data owners approve data use. Model Risk and Control Tower define release rules and who can grant exceptions. An independent release approver signs off.

Tools run tests; the bank controls releases. Convert LangSmith or Arize results to the same format. Keep versioned tests and release rules in bank-controlled storage. If a tool is unavailable and required results are missing, mark the gate incomplete.
